### 1. CrewAI version note (`crewai==1.15.17`, not the tutorial-era `@CrewBase` idiom)

The installed crewai version's `crewai.project.CrewBase` decorator auto-maps **every** entry in the configured `agents.yaml`/`tasks.yaml` against the methods defined on a single crew class (`crewai.project.crew_base.map_all_task_variables`) and raises `KeyError` the moment a task/agent name in the shared YAML doesn't have a matching `@agent`/`@task` method on that specific class. Since this run's task list calls for **one shared `config/agents.yaml`** and **one shared `config/tasks.yaml`** containing all 5 agents/tasks (`pii_guard` + the 4 reasoning-Crew members), but `pii_guard` must be built and invoked as a **separate, standalone Crew** from the 4-agent reasoning Crew (ADR-003), using `@CrewBase` as-is would break the moment `ReasoningCrew` tried to load `redact_pii_task`'s `agent: pii_guard` reference (not defined on that class).

Resolution: `backend/src/app/agents/config_loader.py` is a small manual YAML loader + `Agent`/`Task` factory (documented in its own module docstring) that reads the same shared YAML files and builds plain `crewai.Agent`/`crewai.Task` objects directly — config is still fully externalized to YAML (adapter-crewai.md's rule), just resolved by straightforward Python instead of the decorator. This is a deliberate implementation choice recorded here, not a deviation from adapter-crewai.md's intent.

### 3. PII detection — deterministic tool, agent-invoked (stakeholder-confirmed design)

Per the design decision confirmed before this run started: PII detection is a **deterministic regex/pattern-based pure function** (`backend/src/app/tools/pii_detector.py::detect_pii`), same style as `domain/loader.py`'s `kb_search` — no LLM-only detection. It covers, at minimum, the required set:

- `email` — standard local-part@domain.tld pattern.
- `phone` — North-American-style 10-digit numbers, optional country code/separators, bounded by non-digit lookaround.
- `account_number` — digit sequences (6-19 digits) **preceded by an explicit context keyword** (`account`/`acct`/`confirmation`/`reservation`/`booking`/`card`, optionally followed by "number"/"no"/"#" and a connector like "is"/"was"/":"). This keeps the match explainable and deliberately avoids treating bare digit sequences as account numbers (unit-tested).
- `name` — capitalized 1-3 word sequences following a self-introduction phrase (`my name is` / `I am` / `I'm` / `this is`).

Every detected span returns `(entity_type, span_start, span_end, method)` matching `RedactionAction` in `task_outputs.py` exactly (imported, not redefined). Overlapping candidate spans are resolved deterministically by priority order (`email > account_number > phone > name`), then longest-match, then leftmost — never double-redacted (unit-tested).

`pii_guard` (the CrewAI agent, per ADR-003/ADR-004/SAD §2's agent table) is bound to a `crewai.tools.tool`-wrapped version of this function (`crewai_tools.py::pii_detector_tool`) and invoked via its own standalone 1-agent Crew (`agents/pii_guard.py`) — the agent's task/backstory explicitly instruct it to call the tool once and relay the output verbatim, not to re-detect or paraphrase. `InquiryFlow.pii_redact` (step 2) kicks off this Crew and validates the returned type is a real `RedactionResult`; **any exception or malformed output raises `PiiGuardFailure`**, which the Flow does not catch — it propagates out of `kickoff()` (fail-closed, no unredacted text passed forward, per sad.md §2 Error handling / FR-011). A Diagnostic record is persisted to the interaction log before re-raising, and it **never contains the raw text** (a placeholder string is stored instead) — verified by `tests/integration/test_inquiry_flow.py::test_pii_redact_is_fail_closed_on_pii_guard_failure`, which monkeypatches the pii_guard Crew to fail and asserts both the exception and the redacted-placeholder diagnostic record.

### 5. `max_execution_time` hard ceiling (sad.md §7) — implemented outside CrewAI's `Flow`, not inside it

The installed CrewAI version's `Flow` class (`crewai.flow.runtime.Flow`) has **no native flow-level execution-time cap** — only `Agent.max_execution_time` exists, a different, per-agent-per-task control, not a whole-flow ceiling. `sad.md` §7 requires "Flow-level `max_execution_time` set to 10s" with automatic degrade-to-escalate on expiry.

Resolution: `run_inquiry()` enforces this itself — it submits `InquiryFlow().kickoff(...)` to a single-worker `ThreadPoolExecutor` and calls `.result(timeout=10)`. On `TimeoutError`, it persists an interaction-log record (`outcome="escalated"`, diagnostic noting the ceiling was exceeded) and returns the same escalation-shaped payload the normal `escalate` branch would produce, without raising. This matches sad.md §7's stated behavior ("a stuck or abnormally slow run degrades automatically to the escalate branch rather than hanging indefinitely") even though it isn't literally a CrewAI `Flow` constructor argument. **Known limitation** (Python/stdlib, not a design gap): the underlying flow thread cannot be forcibly killed once started, so a genuinely hung LLM call continues running in the background after the caller receives the timeout-escalation response — acceptable for MVP single-process/no-real-traffic scope (sad.md §7 "Concurrency: not a design driver for MVP"), flagged in Open Questions below.

Verified by `tests/integration/test_inquiry_flow.py::test_run_inquiry_degrades_to_escalate_on_timeout` (monkeypatches `InquiryFlow.kickoff` to sleep past a 1s test timeout; asserts the escalation payload and the persisted diagnostic record).

### 10. `*implement-endpoint` follow-up fix (2026-08-20) — `temperature` 400 on `claude-sonnet-5`, corrected root cause

**Trigger**: a live `POST /chat` call failed with `anthropic.BadRequestError: temperature is deprecated for this model` during `*implement-endpoint` verification, blocking the SAD §7 Latency Spike (which needs clean, error-free live calls to produce valid measurements).

**Investigation**:

- Read `crewai==1.15.17`'s native Anthropic provider (`backend/.venv/Lib/site-packages/crewai/llms/providers/anthropic/completion.py`) — this project's installed CrewAI version uses the `anthropic` Python SDK directly (via the `crewai[anthropic]` extra), **not** LiteLLM, for Anthropic calls (`AnthropicCompletion._prepare_completion_params`: `if self.temperature is not None: params["temperature"] = self.temperature`). No LiteLLM package is even installed in `backend/.venv` — confirmed (`ModuleNotFoundError: No module named 'litellm'`). CrewAI's own code has **no** model-specific guardrail around `temperature` — it forwards whatever is configured unconditionally. The rejection is therefore a **live Anthropic API-side behavior**, not a CrewAI/LiteLLM client-side validation quirk; nothing in the installed `anthropic==0.73.0` SDK validates or blocks `temperature` client-side either (grepped, no matches).
- Reproduced directly against the live Anthropic API (bypassing CrewAI entirely, `backend/.venv`, real `ANTHROPIC_API_KEY` from `backend/.env`), calling `client.messages.create(...)` with `temperature=0.2` for both models, 3 repetitions each:
  - `claude-haiku-4-5` **with** `temperature=0.2` → **OK**, 3/3.
  - `claude-sonnet-5` **with** `temperature=0.2` → **`anthropic.BadRequestError: Error code: 400 - {'type': 'invalid_request_error', 'message': '\`temperature\` is deprecated for this model.'}`**, 3/3 (100% reproducible, not intermittent).

- **Root cause, corrected**: it is `claude-sonnet-5` (used by `sentiment_analyzer` and `response_composer`) that rejects the `temperature` parameter on the live Anthropic API today — the exact opposite of what the `*implement-endpoint` action's live-verification note (§9 above) attributed it to. `claude-haiku-4-5` (`query_classifier`, `knowledge_retriever`, `pii_guard`) has no such restriction and accepts `temperature` normally. The original note's attribution to the Haiku-tier agents was a misdiagnosis made from ad hoc/concurrent live traffic where it wasn't possible to isolate which of the 5 concurrent-ish agent calls actually produced the error; a direct, isolated, repeated probe against the live API resolves the ambiguity definitively.

### 11. `run_inquiry()` double-log fix (2026-08-20) — blocking `shutdown(wait=True)` and duplicate interaction-log rows on timeout, resolved

**Scope**: narrow follow-up fix to the exact defect flagged in §10 above ("New finding, not fixed") and in Open Questions. Touches only `backend/src/app/flows/inquiry_flow.py`, `backend/src/app/persistence/interaction_log.py`, and `backend/tests/integration/test_inquiry_flow.py`. No changes to `POST /chat`, `agents.yaml`, escalation thresholds, or the 10s SAD §7 ceiling value/timeout-escalation behavior itself.

**Two independent problems, two independent fixes**:

1. **Caller blocks past the ceiling.** `run_inquiry()` previously wrapped `pool.submit(...)` / `future.result(timeout=...)` in `with ThreadPoolExecutor(max_workers=1) as pool:`. Python's context-manager `__exit__` calls `pool.shutdown(wait=True)` unconditionally — even when reached via the `except FutureTimeoutError` branch's `return` — so the function did not actually return to its caller until the abandoned background flow thread finished on its own (~15-16s observed), not at the nominal ceiling. **Fix**: the pool is now created and torn down manually (no `with` block); a `finally: pool.shutdown(wait=False)` replaces the implicit `wait=True` shutdown. `shutdown(wait=False)` releases the executor's own bookkeeping without blocking — it does **not**, and cannot, stop the already-running background thread (Python has no API to forcibly kill a running thread; this is the same stdlib limitation already documented in this file's Assumptions/Open Questions, not something this fix tries to solve). The net effect is exactly the one required: `run_inquiry()` itself no longer blocks on that thread's completion.

2. **Duplicate interaction-log row.** Because the background thread cannot be killed, on a real timeout it keeps running and eventually reaches its own `log_interaction` step, which used to call `record_interaction()` with a brand-new `uuid4()` — a second, distinct row for the same inquiry, in addition to the row `run_inquiry()`'s own `except FutureTimeoutError` branch already wrote. **Fix (chosen approach: shared id + idempotent write, not a schema change)**: `run_inquiry()` now mints one `inquiry_id = str(uuid.uuid4())` per call and passes it into `InquiryFlow().kickoff(inputs={..., "inquiry_id": inquiry_id})` — CrewAI's `Flow._initialize_state` merges non-`id` `inputs` keys directly into `self.state` (confirmed by reading `crewai==1.15.17`'s `Flow.kickoff_async`/`_initialize_state` source; note CrewAI's `Flow` already treats a literal `"id"` input key specially for its own state-persistence/restore mechanism, which is exactly why the new key is named `inquiry_id`, not `id`, avoiding any collision with that unrelated CrewAI feature). `InquiryFlow.log_interaction` now uses `self.state.get("inquiry_id") or str(uuid.uuid4())` (the fallback keeps direct `InquiryFlow().kickoff()` callers — e.g. the fail-closed pii_guard test — working unchanged, since they don't seed `inquiry_id`). `interaction_log.py::record_interaction`'s `INSERT` was changed to `INSERT OR IGNORE`, keyed on the existing `id` `PRIMARY KEY` column — **no schema change**. For every normal call site each row still gets a fresh UUID, so this is a no-op change in behavior for all of them; the one deliberate exception is exactly this timeout/straggler race, where `OR IGNORE` makes whichever of the two same-`id` writes lands second a silent no-op instead of a duplicate row — first-writer-wins, order-independent (verified: the synchronous timeout-path write always lands first in practice since it fires at the ceiling, well before the straggler's real completion, but `OR IGNORE` makes the guarantee hold regardless of ordering).

**Why this approach over the alternatives**: an `UPDATE`/upsert-on-conflict (overwriting the timeout row with the straggler's real completion data) was rejected — it would silently rewrite what the caller was actually told (a timeout escalation) into a "responded"/different-outcome row well after the response was already returned, which is worse for NFR-006 auditability, not better: the log should reflect what happened for *that* request/response pair, and the request/response pair the caller received *was* the timeout escalation. A cooperative-cancellation/kill-the-thread approach was explicitly out of scope (stdlib limitation, called out in the task). `INSERT OR IGNORE` keeps the existing one-row-per-`id` schema invariant, requires no migration, and directly encodes "first write for this inquiry wins" — the same semantics as the diagnostic_halt path already uses (a single record per failure mode).

**Test-file change and why**: `test_inquiry_flow_end_to_end_per_scenario_category`'s original `assert len(rows) == 1` counted the *entire* db's rows. Making the two fixes above landed the test at **35 passed** on a clean, isolated single-test run, but the full 4-test parametrized suite still intermittently failed that specific assertion — not because of a dedup failure (verified: with `INSERT OR IGNORE`, at most one row per `inquiry_id` always held), but because of *cross-test* contamination: each parametrized case uses a fresh `tmp_path`-scoped `INTERACTION_LOG_DB_PATH` via `monkeypatch.setenv`, which pytest restores at test teardown; a *prior* test case's still-running, un-killable straggler thread reads `INTERACTION_LOG_DB_PATH` from the environment at write time (not at submission time), so if it finally writes while a *later* test's monkeypatch is active, its row (a different `inquiry_id`, unrelated scenario) lands in that later test's db, inflating its row count. This is a real consequence of the documented "cannot forcibly kill a running thread" limitation surfacing through pytest's per-test env-var monkeypatching, not a flaw in the dedup mechanism. Fix: `run_inquiry()`'s return dict now always includes `inquiry_id` (harmless additive key — `main.py`'s `POST /chat` handler already builds `ChatResponse` from only `result["reply"]`/`result["escalated"]` and ignores extra keys, so this is not an API contract change), and the test now asserts `len([r for r in rows if r["id"] == result["inquiry_id"]]) == 1` instead of `len(rows) == 1` — the same per-inquiry guarantee, without being sensitive to an unrelated scenario's leftover row from a straggler thread outliving its own test's fixture scope.
